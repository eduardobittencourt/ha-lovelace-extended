# Proposal

## Why

The complete synthetic candidate already demonstrates the desk composition, visual editing and bounded input behavior, but cannot send real HA commands. A reversible pilot in the actual installation can now reveal integration, device and usability problems while stage 1 performance acceptance remains open.

## What Changes

- Prepare a separately identified, locally installable desk pilot derived from the fixed-composition candidate. Preserve the synthetic candidate and historical two-slot subject as reproducible references.
- Add a bounded real-service adapter for configured cover controls and three independent button memories, retaining target/data/capability checks, cancellation, single dispatch and truthful feedback. Editing and previews cannot send commands.
- Prepare a reviewed installation manifest, scoped backup and rollback; deploy the pilot resource and one test view in a dedicated pilot dashboard during apply. Preserve the current desk card and dashboard default.
- Reverify the installation's actual roles and frontend contracts before dependent integration; validate visual configuration, live data, errors and recovery without intentionally disrupting production entities or connectivity.
- Exercise the reference device and operator-supervised desk commands, with current external lock prerequisites and separate command/state/movement observations. Capture initial use feedback without declaring everyday replacement acceptance.
- Update stage 2 documentation from actual outcomes. Pilot entry does not require closing every stage 1 metric; failed/unsupported performance rows remain open, and relevant pilot measurements cannot be relabeled final acceptance.

## Capabilities

### New Capabilities

- `real-ha-card-operation`: Reversible installation and bounded real operation of the complete card in an HA test view, including preview suppression, service feedback and staged pilot evidence.

### Modified Capabilities

None. `fixed-composition-card` retains its synthetic-only boundary; `independent-element-bindings` retains its historical two-slot scope. The pilot derives their functional behavior without enabling transport in either historical subject.

## Impact

- Planned implementation: `pilots/desk-card/`, with its own module entry, custom-element discriminator, visual form, adapter, tests and installation/validation guide. Start with the candidate's plain JavaScript approach; this is no general production stack or public configuration commitment.
- Planned documentation: root README, roadmap, decisions, discovery, MVP status and candidate handoff, distinguishing pilot availability from completed MVP acceptance.
- Apply may modify the real installation only through the bounded resource/test-view plan after read-only preflight and preparation of reviewable changes. Existing cards, default dashboard, integrations, firmware, locks and HA version remain outside the change. No HACS publication, release, dependency/toolchain upgrade or HA restart is planned.
- Actual versions, role mappings, resource mode, preview signal and browser behavior are execution gates; historical observations are not current installation verification. Sources and specific checks are recorded in research.md.
- Raw captures, installation scripts and private backups stay outside the checkout; publish sanitized scenario findings and portable aliases only. Existing Apache-2.0 and third-party notices continue to apply.
- Non-goals: resolving every stage 1 failure, adopting production architecture/support/distribution policies, changing locks automatically, replacing the existing desk solution, or claiming full MVP/everyday acceptance.

This request authorizes planning only. A subsequent apply request starts implementation and the scoped pilot workflow; physical execution additionally waits for the operator's readiness for the recorded session. No HA mutation or desk movement occurs during proposal creation.
